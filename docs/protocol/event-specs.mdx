# NSM Event Specifications

This document provides comprehensive technical specifications for all event types in the NSM (Nostr State Machine) protocol.

## Overview

The NSM protocol defines three event kinds that work together to create a complete collaborative state machine system:

| Kind | Type | Purpose | Replaceability |
|------|------|---------|----------------|
| 30079 | Definition | Application schema and metadata | Parameterized Replaceable |
| 7000-7999 | Interaction | User actions and state transitions | Regular (Immutable) |
| 10079 | State Update | Canonical state snapshots | Replaceable |

## Event Kind 30079: NSM Definition

### Purpose

Definition events establish the foundational rules, schemas, and metadata for an NSM application. They serve as the "constitution" that governs how the application behaves and what valid states and interactions look like.

### Replaceability

These are **parameterized replaceable events** (NIP-33), meaning newer events with the same `d` tag replace older ones. This allows application developers to update their application definitions while maintaining the same identifier.

### Tag Specifications

#### Required Tags

| Tag Name | Format | Validation Rules | Example |
|----------|--------|------------------|---------|
| `d` | `["d", identifier]` | Non-empty string, unique per pubkey | `["d", "collaborative-todo-v1"]` |
| `name` | `["name", appName]` | Human-readable application name | `["name", "Collaborative Todo App"]` |
| `engine` | `["engine", engineId]` | State machine engine identifier | `["engine", "xstate"]` |
| `engineCodeURI` | `["engineCodeURI", uri]` | Valid URI to engine implementation | `["engineCodeURI", "https://cdn.example.com/app.js"]` |

#### Optional Tags

| Tag Name | Format | Validation Rules | Example |
|----------|--------|------------------|---------|
| `ui-spec` | `["ui-spec", uri]` | Valid URI to UI specification | `["ui-spec", "https://example.com/ui.json"]` |
| `version` | `["version", semver]` | Semantic version string | `["version", "1.2.0"]` |
| `description` | `["description", text]` | Application description | `["description", "Real-time task management"]` |

### Content Schema

The `content` field contains JSON with the following structure:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "initialState": {
      "type": "object",
      "description": "Initial state of the state machine"
    },
    "stateSchema": {
      "type": "object",
      "properties": {
        "type": {"const": "object"},
        "properties": {"type": "object"},
        "required": {"type": "array"}
      },
      "required": ["type"],
      "description": "JSON Schema defining valid state structure"
    },
    "interactionSchema": {
      "type": "object",
      "properties": {
        "type": {"const": "object"},
        "properties": {"type": "object"},
        "required": {"type": "array"}
      },
      "required": ["type"],
      "description": "JSON Schema defining valid interaction structure"
    }
  },
  "required": ["initialState", "stateSchema", "interactionSchema"]
}
```

### Validation Rules

1. **Tag Validation**: Must contain all required tags with non-empty values
2. **Content JSON**: Must be valid JSON that parses without errors
3. **Schema Validation**: Both `stateSchema` and `interactionSchema` must be valid JSON Schemas
4. **URI Validation**: `engineCodeURI` and optional `ui-spec` must be valid URIs
5. **Identifier Uniqueness**: The `d` tag value should be unique per pubkey to avoid conflicts

## Event Kinds 7000-7999: NSM Interaction

### Purpose

Interaction events represent user actions that should trigger state machine transitions. They form an immutable event log that can be replayed to reconstruct application state.

### Kind Assignment Algorithm

Kinds within the 7000-7999 range are assigned deterministically to avoid conflicts:

```javascript
function getInteractionKind(appAddress) {
  // Create hash from app address
  const hash = Array.from(appAddress).reduce((acc, char) => {
    return ((acc << 5) - acc + char.charCodeAt(0)) & 0xffffffff;
  }, 0);

  // Map to 7000-7999 range
  return 7000 + (Math.abs(hash) % 1000);
}

// Example usage
const appAddress = "30079:abc123...:my-app";
const kind = getInteractionKind(appAddress); // e.g., 7234
```

## Event Kind 10079: NSM State Update

### Purpose

State Update events represent canonical state snapshots after applying interaction events. They enable efficient synchronization and provide conflict resolution for collaborative applications.

### Replaceability

These are **replaceable events** (NIP-16), meaning newer events replace older ones. This allows the canonical state to be updated while maintaining a single source of truth.

1. **State Schema Conformance**: The `state` object must conform to the `stateSchema` from the referenced Definition event
2. **Address Reference**: The `a` tag must reference a valid Definition event

4. **Interaction Reference**: `lastInteractionId` should reference a valid Interaction event (if present)
5. **Arbiter Authority**: If `arbiter` tag is present, the event should be signed by that pubkey or authorized by them

## Common Validation Patterns

### Event Signature Validation

All NSM events must have valid Nostr signatures:

```javascript
async function validateEventSignature(event) {
  const eventHash = await sha256(JSON.stringify([
    0,
    event.pubkey,
    event.created_at,
    event.kind,
    event.tags,
    event.content
  ]));

  return await schnorr.verify(event.sig, eventHash, event.pubkey);
}
```

### Schema-Based Content Validation

Content must be validated against the schemas defined in Definition events:

```javascript
function validateInteractionContent(content, definitionContent) {
  const { interactionSchema } = JSON.parse(definitionContent);
  const interaction = JSON.parse(content);

  return jsonSchemaValidator.validate(interaction, interactionSchema);
}

function validateStateContent(content, definitionContent) {
  const { stateSchema } = JSON.parse(definitionContent);
  const stateUpdate = JSON.parse(content);

  return jsonSchemaValidator.validate(stateUpdate.state, stateSchema);
}
```

### Address Tag Validation

Address tags must reference valid Definition events:

```javascript
function validateAddressTag(addressTag) {
  const pattern = /^30079:[a-fA-F0-9]{64}:.+$/;
  return pattern.test(addressTag);
}

function parseAddressTag(addressTag) {
  const [kind, pubkey, identifier] = addressTag.split(':', 3);
  return {
    kind: parseInt(kind),
    pubkey,
    identifier
  };
}
```

## Performance Considerations

### Event Size Limits

While Nostr doesn't strictly limit event sizes, NSM implementations should consider:

- **Definition Events**: Typically 1-10KB for schemas and metadata
- **Interaction Events**: Should be kept under 1KB for optimal relay performance
- **State Update Events**: May be larger (10-100KB) but should be optimized for critical state only

### Validation Caching

Implementations should cache validation results to avoid repeated computation:

```javascript

  constructor() {
    this.definitionCache = new Map();
    this.schemaValidatorCache = new Map();
  }

  async validateEvent(event) {
    // Cache definition events and their schemas
    // Reuse compiled schema validators
    // Cache signature validation results
  }

```

### Efficient State Synchronization

State Update events should include metadata to enable efficient synchronization:

- Use `stateVersion` for version-based synchronization
- Include `appliedInteractions` to track which events have been processed
- Provide `canonicalStateHash` for integrity verification without full state comparison
